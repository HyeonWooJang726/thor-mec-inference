# Local in-flight Calibration04 C5 extension preregistration

Calibration03 measured the same full Local pipeline at C_L=1,2,3,4 with K=8×30 FPS, B=1 and a 240-FPS source. Its two-repeat means were 178.675, 210.4833, 232.2333 and 234.3667 FPS, respectively, and all C values were 2/2 SATURATED_VALID. Those results are immutable historical context. Calibration04 independently repeats C3 and C4 alongside new C5 in one session to ask whether the observed flattening continues and how queue wait, service time and GPU span change. C_L remains a deployment configuration, not a main research decision variable.

The sole intervention is C_L∈{3,4,5}. Exact six-run order: `LINFLIGHT04_C3_R1`, `LINFLIGHT04_C4_R1`, `LINFLIGHT04_C5_R1`, `LINFLIGHT04_C5_R2`, `LINFLIGHT04_C4_R2`, `LINFLIGHT04_C3_R2`. Each run is Local only, uses the same eight source videos at 30 FPS/stream, decode, preprocess, model/engine, ready queue, TensorRT batch B=1, MAXN, CUDA Graph OFF, SpinWait OFF, TRT streams=1 per worker, GPU 1575 MHz, pruning OFF, 60-second active interval, 30 warmup inferences per worker, complete drain and a minimum 10-second idle. Thor's seven CPU policies are manually pinned performance/min=max 2601000 kHz and manually restored to schedutil/min=972000/max=2601000 kHz after success, failure or interruption and before analysis. No Edge or network workload. Expected workers/contexts/warmups are C3=3/3/90, C4=4/4/120, C5=5/5/150.

Each run records active completion FPS, source-arrival FPS, g_B_H, Delta_FPS, supply class, queue-wait p50/p95, service mean/p50/p95, GPU span mean/p95, host residual mean/p95, active-concurrency mean/p95/peak, observed GPU frequency and target fraction, CPU validity, temperature if available, OC3 delta and integrity. `SATURATED_VALID` requires VALID, all 240-FPS source work admitted and raw `UNSUSTAINABLE` (g_B_H>0.5 frame/s AND Delta_FPS>0.5 FPS). `SOURCE_LIMITED` requires VALID, raw `STABLE`, and active completion ≥239.5 FPS. Other VALID runs are `AMBIGUOUS`. INVALID is excluded from performance inference and stops later workload; SOURCE_LIMITED/AMBIGUOUS do not stop the fixed campaign.

Let r3,r4,r5 be the new two-repeat means. Final deployment C selection follows this hierarchy, fixed before any Calibration04 workload:

1. Any INVALID measured run gives `NO_C_SELECTION_INVALID_DATA` and no C. Each C must have two valid repeats with the same supply class. Mixed repeat classes such as SATURATED_VALID/SOURCE_LIMITED or SATURATED_VALID/AMBIGUOUS give `C_LEVEL_REPEAT_AMBIGUOUS` and no C.
2. If one or more C values are **2/2 SOURCE_LIMITED**, select the smallest such tested C. The primary verdict is `FULL_LOAD_SUSTAINABLE_C_SELECTED`. This means that C sustains the 240-FPS deployment offered load under the frozen raw `STABLE` and active-completion ≥239.5 FPS definition. It does not estimate true saturated capacity above 240 FPS. One SOURCE_LIMITED repeat alone never qualifies a C.
3. If C3, C4 and C5 are all **2/2 SATURATED_VALID**, apply the saturated plateau rule. If r5>1.02×r4, report `PLATEAU_NOT_REACHED_AT_C5_SCAN`, choose no C and only propose C6. If r5≤1.02×r4, calculate `rmax=max(r3,r4,r5)`, mark C eligible when rC≥0.98×rmax, select the smallest eligible C, and report `SATURATED_PLATEAU_C_SELECTED`. This supports a C3–C5 throughput plateau within the stated engineering tolerance.
4. On the all-saturated branch, apply the same plateau/selection rule separately to each repeat. If a repeat-level branch or selected C differs from the two-repeat-mean result, report `REPEAT_AMBIGUOUS` and choose no C. No third repeat or C6 is automatic.

If no C is 2/2 SOURCE_LIMITED and at least one C is 2/2 AMBIGUOUS, the two-repeat supply evidence cannot resolve either selection branch. Report `REPEAT_AMBIGUOUS`, choose no C, and set `repeat_ambiguity_kind=TWO_OF_TWO_AMBIGUOUS_SUPPLY` to distinguish this case from discordant repeat classifications. This conservative fallback does not relabel a VALID run as INVALID.

The six-run order, offered load, runtime, warm-up, metrics and production finalizer remain unchanged. Queue wait, service time, GPU span, host residual, active concurrency and temperature are supporting characterization, never a second selection objective. OC3 is diagnostic only. Do not create a post-hoc weighted score.

`tradeoff_summary.csv` reports per-C mean completion FPS, gain versus previous C, queue wait, service, GPU span, host residual, concurrency and OC3 R1/R2/mean. These secondary metrics explain observed costs; they do not change the throughput verdict or form a post-hoc composite score. OC3 is diagnostic telemetry only and cannot reject a C or prove causality. Temperature is also non-decisional. The figure source is for one compact two-panel throughput/service-or-queue figure, excluding OC3.

Calibration04 does not claim a global C5 optimum, C6–C8 behavior, automatic service-cost increase, causal OC3 effects, or a new novelty variable. Synthetic/replay regression establishes validator/finalizer structure only; approved future six-run measured data alone can support a performance claim. Calibration01–03 results and verdicts remain unchanged.
