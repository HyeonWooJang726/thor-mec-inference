# Local in-flight calibration03 — C_L=2 deployment justification preregistration

Calibration01 ran only `LINFLIGHT01_C1_R1` and stopped at an INVALID post-run warmup audit. Calibration02 ran only `LINFLIGHT02_C1_R1`; its child passed, but its parent finalizer applied the stale C=2 warmup count. Both failed attempts are immutable. No valid calibration performance outcome has been observed; 175.13 and 174.05 FPS are not performance evidence. Calibration03 is a fresh, unobserved campaign. It asks whether the C_L=2 deployment setting used by Grid02 and Confirmation02 is reasonable under the same full Local path. It does not seek every C's true maximum capacity, create a controller variable, or retrospectively change those valid C_L=2 results. The immutable calibration01 `SATURATION_GUARD_REVIEW.md` remains correct: K8×30 can censor C3/C4 capacity.

The sole tested intervention is C_L in {1,2,3,4}, with two repeats per C. Exact order and run IDs: LINFLIGHT03_C1_R1, C2_R1, C3_R1, C4_R1, C4_R2, C3_R2, C2_R2, C1_R2 (each abbreviation retains the LINFLIGHT03_ prefix). All runs use the same eight synchronized 30-FPS source videos, all 240 frames/s admitted Local, pruning OFF, Edge OFF, physical decode/preprocess, model/engine and TensorRT batch one. Same 60-s active window, 30 warm-up inferences per active worker, complete drain, and 10-s post-cleanup idle. MAXN, GPU 1575 MHz, CUDA Graph OFF, SpinWait OFF, one CUDA stream per active worker, seven CPU policies performance/min=max 2601000 kHz during measurement, manual restore to schedutil/min=972000/max=2601000 kHz before analysis. No source, K, FPS, fixed-tensor, closed-loop or synthetic-supply change is permitted.

The exact frozen V2.2 worker source constructs two contexts before appending workers 2..C. The calibration-only binding uses `ConcurrentTensorRT(engine,min(c,2))` for the initial context count, then the same append loop. It still uses the same ContextWorker class and the same inference/queue/decode/measurement statements; for C>=2 the constructor argument remains the original 2. The derived worker SHA and frozen base SHA are separate. Child and parent finalization both bind the calibration-only C-aware summary adapter: expected warmup is planned C times recorded warmup per worker, and active concurrency must not exceed planned C. Parent finalization also checks worker/context/phase cardinality with the helper used by the offline analyzer. Frozen V2.2 summary and historical results remain unchanged. `PARENT_FINALIZER_FIX.md` and `PRODUCTION_PATH_C_AUDIT.md` document the validation paths.

For every run report active completion FPS (drain excluded), source arrival FPS, backlog slope g_B_H over the final 30 s, whole-active deficit Delta_FPS, supply class, queue p50/p95, service mean/p50/p95, GPU span mean/p95, host residual mean/p95, concurrency mean/p95, OC3, observed GPU frequency/target fraction, CPU before/after, temperature and integrity. Deadline TIR is not primary. Supply classes retain the original raw-scan rule: `SATURATED_VALID` is VALID/240 admitted with raw UNSUSTAINABLE (g_B_H>0.5 and Delta_FPS>0.5); `SOURCE_LIMITED` is VALID/raw STABLE with completion >=239.5 FPS at the 240 ceiling; other VALID runs are `AMBIGUOUS`. Invalid runs are never performance evidence. Unlike the superseded global-plateau rule, a valid source-limited or ambiguous run does not stop the remaining fixed comparison; first INVALID stops later workload. No retry/resume/overwrite.

For complete 8/8 VALID data, let r_C be each C's two-repeat mean active completion FPS; T_2=r_2/0.98. The old C2 214.47-FPS result is not used as the threshold. Apply these pre-registered checks in order, with one primary verdict. (A) If r_1>=0.98*r_2, `C_L2_NOT_MINIMAL`. (B) Otherwise, if either r_3 or r_4 is strictly greater than T_2, `C_L2_REJECTED_HIGHER_C_REQUIRED`, even if that higher C is source-limited: observed throughput is already a lower bound that rejects C2. Do not choose between C3 and C4. (C) Otherwise, if any C lacks 2/2 SATURATED_VALID supply evidence, `C_L2_INCONCLUSIVE_SOURCE_CEILING`; in particular higher-C source limitation or ambiguity can never justify C2. Requiring C1/C2 evidence here also prevents a false justification from an uncertain comparator/reference. (D) Otherwise, `C_L2_DEPLOYMENT_JUSTIFIED`. If individual repeat verdicts disagree with each other or their mean-based verdict, override the primary verdict with `CALIBRATION_REPEAT_AMBIGUOUS` and propose only implicated C values for a separately approved third repeat. Incomplete/INVALID data receive no primary performance verdict.

Only when all four C values are 2/2 SATURATED_VALID, calculate the auxiliary global observed plateau using epsilon=0.02 and smallest C with r_C>=0.98*max(r_C); when C2 is justified it must agree. This auxiliary calculation never selects a higher-C final winner after C2 rejection and triggers no automatic C5, higher-supply harness, or repeat. Queue/service/GPU span are explanatory metrics only, not criteria that override the throughput verdict. A source-limited higher C may reject C2, but cannot establish the higher C's true maximum capacity. A source-limited higher C below T_2 leaves C2 inconclusive.

Only a measured `C_L2_DEPLOYMENT_JUSTIFIED` result may support the restricted paper wording about selecting C2 within 2% of the throughput relevant to its decision. Do not claim universal optimality, GPU kernel parallelism from C alone, deadline equivalence, C_E optimality, or unmeasured CPU preprocessing causality. At most one two-panel paper figure is planned; the analyzer will generate its source CSV after the workload. The future operator must obtain a read-only GPU sysfs permission check PASS before CPU pin. Calibration03 requires C1–C4 synthetic replay through the actual production parent-finalizer code, negative finalizer fixtures, read-only Calibration02 real-raw replay, and legacy C2 compatibility to PASS before READY. Synthetic results are never performance evidence. No workload, clock change, sudo or network action occurs during this preparation.
