# Edge E48 Confirmation01 — frozen preparation

This is an Edge-only calibration for the Block B candidate splits L208E32, L200E40 and L192E48. It does not prove hybrid capacity. The frozen Edge backend, RAW640 payload (691,200 bytes), D=100 ms, C_E=1, batch=1, synchronized K=8 × 30 FPS source, and Thor CPU 7-policy performance/min=max=2,601,000 kHz control match Final02. Edge endpoint is the operator-verified `192.168.0.6`; the Edge operator must confirm its live address matches the plan before CPU pin. No session was run during preparation.

The canonical floor masks come from `campaign_config.schedule(rate, 0, 'ALIGNED')`: E48 uses q6 (6/30 frames per stream), E64 uses q8 (8/30). ALIGNED E48 uses phases `[0,0,0,0,0,0,0,0]`; STAGGERED E48 and E64 use the fixed `[0,1,2,3,4,5,6,7]`. Phase changes which current source frame is selected; source arrival and admission timestamps are not shifted, frames are not held, and stream dispatch order remains canonical. The masks, slot counts and hashes are in the pattern JSON files.

Preparation computed E48 ALIGNED slot histogram `0:24, 8:6`. E48 STAGGERED has `1:12, 2:18`, hence max slot load 2 equals the theoretical bound ceil(48/30)=2. E64 STAGGERED has `2:26, 3:4`. This is a fixed-phase result, with no claim about globally optimal phase or variance.

The server and client session order is exact: one 15 s `EDGE48C01_WARMUP_E48_S`, then E48 `A1 S1 S2 A2 A3 S3 S4 A4 A5 S5`, then E64 STAGGERED `S1 S2 S3`. Every measured session is 30 s. At least 10 s idle follows each session's cleanup before the next one. Warm-up integrity, server drain and Thor pending at active end must pass before A1. Warm-up contributes no repeat, TIR statistic, paired difference or capacity classification. E64 starts only if all ten E48 sessions are VALID; it is descriptive regardless of its TIR. First INVALID stops later sessions. No retry, resume or overwrite.

For each E48 pattern, `ROBUST_EDGE_USABLE` requires 5/5 VALID TIR_admission ≥ 0.90; `ROBUST_EDGE_FAIL` requires 5/5 VALID TIR_admission < 0.80; other valid outcomes are `ROBUST_EDGE_BOUNDARY`. The 5/5 rule is an engineering confirmation rule, not a significance test. Exact terminal identity is admitted = timely + late completed + expired, with no true unfinished after drain. Invalid network/protocol or integrity outcomes are not capacity failures.

The five descriptive pairs are fixed `(Ai,Si)`, each delta `TIR(Si)-TIR(Ai)` even for the reversed execution direction of pairs 2 and 4. Paired differences never enter robust classification. Report all five TIRs per E48 pattern, mean/median/min/max/sample SD, timely FPS, worst-stream TIR and fixed-order fairness metrics; E64 gets three values plus mean/min/max/sample SD and worst-stream TIR, with no robust capacity label. Mechanism expectations are separate non-binding diagnostics.

Thor `check` validates frozen SHA and cache, fresh namespace and CPU baseline; route lookup is hard, neighbor and ICMP are diagnostic. It never opens port 5000. Exact Edge stdout `LISTENING 5000: 14 CONFIRMATION sessions`, Edge-local `ss` listener evidence, Edge→Thor evidence transfer, Thor `listener-confirmed`, and a pinned CPU readback are hard prerequisites before the first real client protocol session (warm-up). CPU restore PASS is required before analysis. Use the deployment documents and the [Thor–Edge runbook](/home/ainet/research/thor-mec-rate-dvfs-gate/docs/testbed/THOR_EDGE_CONNECTION_RUNBOOK.md).

The approx. 5.8 Mbit/frame wire diagnostic implies ~278 Mbps at E48 and ~371 Mbps at E64; ALIGNED 8-frame serialization at D100 with 9–10 ms server service suggests ~510–520 Mbps in a simplified model. These are pre-registered expectations, not measured bounds or gates. The Final02 ~337 Mbps figure is one run's observed transmitted-data rate, not PHY rate.
